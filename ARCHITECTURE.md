# Architecture

METIS is an Android-only, local-first personal assistant. The [Phase 0 contracts](docs/PRODUCT_CONTRACT.md) define its planned behavior. Phases 1–3 supply the Android scaffold, design system and navigation shell. Phase 4 supplies all 22 planned Room tables and saved-data screens; Phase 5 adds manual memory workflows. Phase 6 establishes the typed agent pipeline. Language parsing, platform execution and ML remain later gates.

## Boundaries

`MainActivity` handles the Android lifecycle, edge-to-edge window setup, and IME resizing. `presentation/navigation/AgentApp` collects immutable `ShellUiState` from `ShellViewModel` with lifecycle-aware StateFlow collection. Its five typed top-level destinations are Today, Plan, Agent, Timeline, and You. Phones use bottom navigation; wide, short landscape, or large-font windows use a scrollable rail. Scaffold padding is consumed before child layouts handle system/keyboard insets.

Navigation is intentionally limited to five top-level destinations and the informational privacy detail. It has no external deep links or arbitrary route strings. The detail keeps its source destination; Back dismisses input/detail before returning to Today, where Android handles leaving the app. Per-destination scroll state is kept using a saveable state holder.

One shared composer sheet edits an unsent draft from any destination or privacy detail. Button and IME submission create the same typed AgentRequest through RequestViewModel. The current UnsupportedLanguage baseline returns an explicit unsupported result without guessing an intent. SavedStateHandle stores destination, bounded unsent draft (4,000 UTF-16 code units), and visibility only. Submission clears that draft. Requests and results stay in RAM, clear on sheet dismissal, and are never written as conversations or memory. Busy state prevents simultaneous submissions; dismissing cancels processing. No microphone integration exists.

The design system renders supplied display models and emits callbacks. It never authorizes actions, parses commands, grants permissions, or writes storage. `ProposalDisplay`, `ReceiptDisplay`, and `ComposerState` are presentation data, not the Phase 6 domain protocol. A proposal is unavailable by default; the future domain supplies current acceptance authority. Handoff/pending receipts are visibly unverified, and undo appears only when a callback is supplied.

The isolated `DesignSystemTestActivity` and synthetic component gallery are debug-only. The host is exported for emulator visual review, has no side effects or user data, and is absent from release. Production `MainActivity` never shows synthetic tasks or receipts.

Future package/module dependencies follow presentation -> agent/domain -> repository interfaces -> data/platform adapters. The domain owns AgentRequest, typed actions, policy decisions, receipts, and events. Text and voice use one orchestrator. Android integrations implement replaceable interfaces. Hilt, Room, DataStore, and WorkManager are introduced when a phase actually needs them, not as unused dependencies.

`domain/storage` defines validated immutable records and repository interfaces for tasks, schedules, memories, task dependencies and preferences. `data/storage` implements them with one app-scoped Room connection, transaction-protected revision checks, indexed queries, SQL integrity triggers, and SET NULL schedule/task links. Sensitive task titles/notes, schedule titles/reasons, memory content and preference values are versioned AES-GCM BLOB envelopes. AAD binds each field to its table, UUID, and column. Missing keys, failed encryption, or invalid data fail without destructive fallback; populated storage must decrypt an existing field before any write. No persistent plaintext search index exists.

`RecordsViewModel` observes repository Flows off the main thread and publishes loading/data/error state independently of transient navigation. Today lists saved tasks (including future/undated tasks); Plan lists saved blocks with explicit zones and statuses; You labels explicit versus derived memory. Tasks and schedules are read-only until policy/protocol mutations arrive; Phase 5 enables explicit manual memory CRUD. Storage errors discard decrypted display rows and expose retry without logging exception content. Timeline observes saved normalized events. Only the debug source set includes synthetic seed/inspection code; seeding is explicit, transactional, and rejects nonempty databases. Release has no seed or inspection implementation.

Physical schema v2 adds paired memory entity references and their index, with an explicit data-preserving 1 -> 2 migration that restores integrity triggers. Task/schedule deletion also deletes explicitly linked memory in the same transaction. Memory search selects bounded, unexpired metadata candidates, decrypts them on IO, builds FTS4 on an isolated SQLite `:memory:` connection, and closes it after each query. Literal Unicode-word MATCH input is bound; candidate/output truncation is surfaced. You's search query/result state is transient, debounced, cancelled on edits, and refreshed when saved data changes. Search excludes expired records; saved-record browsing remains an archive, with retention and Phase 5 ranking still pending.

Personal storage is app-private, with sensitive fields protected using Keystore-backed authenticated encryption. The manifest disables backup and cleartext traffic and requests no permissions. Explicit legacy and modern backup rules exclude both credential/device-protected storage and device transfer. The debug Compose tooling dependency may add an internal signature permission; it grants no network or dangerous access.

Physical schema v3 adds explicit task prerequisite edges with unique pairs and cascading task foreign keys. A separate dependency repository validates endpoint existence, optimistic revisions, and iterative cycle detection in one write transaction. Dependency reads/writes use the same existing-key guard. Today observes saved prerequisite counts; the UI makes no readiness or planning decisions. The explicit v2 -> v3 migration creates an empty graph without rewriting existing encrypted fields; v1 upgrades chain through v2.

Physical schema v4 adds a registered, typed EXPLICIT preference store with encrypted values, unique keys, immutable key identity and optimistic revisions. Supported inputs are day start time, focus-block minutes and week start day; authority/consent settings are outside this registry. You observes saved preferences with the existing loading/error boundary. The readable-key guard includes preference-only databases, and debug empty-storage checks count preferences. Explicit v3 -> v4 migration creates no inferred defaults and preserves existing encrypted fields and graph edges. Future specialist training follows the [training plan](docs/AGENT_TRAINING_PLAN.md); no model is enabled by persistence work.

## Build

Gradle Kotlin DSL and `gradle/libs.versions.toml` hold the pinned plugin/dependency versions. Gradle 8.11.1, AGP 8.10.1, Kotlin 2.1.20, and the matching Kotlin Compose compiler plugin build against API 36, with minimum API 26 and Java/Kotlin bytecode target 17. Release enables R8 optimization and is unsigned; no signing key is stored in the repository.

CI runs compilation, debug/release lint with warnings treated as errors, JVM privacy/contrast regressions, Detekt static analysis, and instrumented APK compilation. Separate emulator jobs run launch/recreation, packaged privacy, and component interactions on APIs 26 and 36. The Phase 1 [recovery run](https://github.com/raghavkp2006-ux/metis-android-agent/actions/runs/37465741379) passes all three jobs; Phase 2 has a separate verification record.

Keep the [roadmap](docs/ROADMAP.md) phase gates explicit. A launchable scaffold is not a working reminder agent.

Schema v6 extends the database to all planned foundations. Generic typed repositories share revision/key guards, while record-specific validation enforces stable action identity, references and append-only history. FoundationOutcomes saves correlated action/event/audit records atomically. FoundationPrivacy traverses linked records iteratively before root deletion and FK cascades; encryption or revision failures roll back deletion and cleanup together. Saved profile/people, time records and Timeline use lifecycle-aware repository observation and clear decrypted display state on failure. Behavioral repositories remain blocked and no stored value grants platform authority. See the [Phase 4 completion report](docs/PHASE_4_COMPLETION.md).

Phase 5 MemoryEngine coordinates explicit local edits, structured/linked retrieval, working context and reviewed retention. InMemoryMemorySearch filters metadata before bounded decryption, then matches temporary FTS records and ranks eligible matches with a pure deterministic domain policy. Scores contain IDs and normalized numeric components without copying content. MemoryEditorViewModel keeps personal drafts in RAM, discards them on screen exit/recreation and handles stale writes without overwriting newer records. Expiry deletion revalidates a metadata snapshot inside one transaction and invokes existing linked-content cleanup. Schema v6 is unchanged; no scheduler, action dispatcher or ML runtime is introduced.

Phase 6 domain/agent owns validated requests, extraction/context, all 14 sealed action variants, expiring proposals, result/receipt/event models, and replaceable classifier/extractor/context/specialist/policy/executor interfaces. LocalAgentOrchestrator has no executor or repository dependency: it stops negated/unknown/unresolved inputs and routes suggestions through proposal policy. Collections are defensively frozen; original text and UTF-16 offsets are checked. The shipped context reports answer-only authority and no implemented agent capabilities, independently of dormant stored profile settings. ProposalPolicy reviews risk, current capabilities and revisions but grants no dispatch authority. Phase 8 must supply binding acceptance, fresh platform checks, durable idempotency/reconciliation and transactional adapters; Phase 9 adds event serialization/persistence. Existing encrypted storage representations are unchanged.
