# Privacy

METIS keeps raw and derived personal data on the user's Android device. Physical schema v7 retains the 22 existing record types and adds three explicit discipline tables in an app-private Room database. Personal text uses Keystore-backed AES-GCM encryption with fresh nonces and authenticated row/column bindings; no plaintext search duplicate is stored. The app persists no conversation or raw microphone audio and has no account, analytics SDK, advertising SDK, backend or internet permission. Speech uses an Android on-device recognizer when available; online fallback is disabled by default and requires explicit opt-in in Settings. If enabled and needed, Android may send audio to its speech provider. METIS keeps only the editable transcript in the unsent draft until the user presses Send. Notification access remains optional for approximate reminders.

## Current safeguards

- Android backup is disabled; legacy backup and Android 12+ cloud/device-transfer rules exclude personal storage domains.
- Cleartext traffic is disabled. The installed permission set excludes internet and all unrelated dangerous runtime permissions; notification permission is the explicit reminder exception.
- The app contains no telemetry or remote reporting client. Build tools download public dependencies during development; that is separate from app runtime behavior.
- Reads/writes that cannot decrypt existing data fail visibly without resetting storage or replacing its key. Storage errors and personal content are not logged. Metadata such as IDs, dates, status, zones, and confidence remains unencrypted in app-private storage.
- Production opens an empty database without synthetic records. Only debug builds offer explicit synthetic seeding and on-screen record counts, with no content logging or export. Saved-data lists observe local records. Explicitly confirmed task creation/completion and guarded undo can change tasks; schedules and factual timeline history remain read-only. Memory supports explicit manual add/edit/delete with reviewed deletion. Phase 14 adds a separate default-off, local behavioral-analysis consent switch; daily/weekly reflection runs only on user request and reads normalized event types and timestamps, never event payloads or private text. Withdrawal disables analysis before deleting derived insights and habits.
- Local memory search decrypts a bounded metadata-filtered candidate set and builds an isolated in-memory FTS4 index that is closed after each query. Search text/results are transient ViewModel state, never SavedStateHandle or a disk search mirror. Physical v1 -> v2 migration preserves encryption; deleting a task or schedule also removes explicitly linked memory content in the same transaction.
- Release artifacts are unsigned development outputs, not a store-ready application.
- Task prerequisites store only structured UUID links and record metadata in schema v3. The repository checks key readability before observation or mutation; deleting either task cascades its links. The explicit upgrade leaves encrypted personal fields unchanged and creates no inferred prerequisites. No device permission or planner/action capability is added.

Physical schema v4 stores only explicitly supplied, registered planning preferences. Values are Keystore-encrypted BLOBs; key/type/version/source metadata is unencrypted app-private structure. Preference-only storage participates in the existing readable-key guard, so key loss blocks new writes without generating a replacement key. You displays saved values without inferring defaults or enabling behavioral analysis. Autonomy and consent cannot be changed by this preference registry. These values are not uploaded or used for model training.

## Future capabilities

Reminder scheduling and notification posting stay local. Future calendar context and behavioral statistics must also remain local. Sensitive fields must retain Keystore-backed encryption. Contact/calendar/microphone/notification access is requested progressively for an enabled feature, with denial paths. Behavioral analysis and dataset contribution require explicit consent; contribution must redact private content and identifiers. No default private telemetry.

Opening a dialer, maps app, calendar editor, or messaging composer hands selected information to another app only after the applicable policy/confirmation checks. That app's privacy policy applies after the handoff. System speech recognition is not assumed offline: METIS uses the on-device recognizer where available, explains the microphone purpose before requesting RECORD_AUDIO, and requires the separate online-fallback opt-in before using a general Android recognition service. METIS neither persists nor uploads raw audio. A transcript remains an editable draft and is not submitted automatically.

Encrypted export/import and synchronization are not implemented. Neither raw data nor derived data is sent to a cloud service by default. Device-specific backup behavior and storage protections require further device testing before production; this scaffold does not claim forensic secure deletion or full production security certification.

The [product contract](docs/PRODUCT_CONTRACT.md) and [database contract](docs/contracts/DATABASE_V1.md) define the requirements for future phases. Update this document whenever actual data handling changes.

Phase 5 adds configurable deterministic memory ranking, structured retrieval and explicit/derived filters. Derived provenance is immutable in ordinary updates. Working memories saved through the engine expire within 24 hours; expired items stay archived until explicit deletion. Expiry review reads a bounded metadata snapshot only, and confirmation rechecks every ID/revision/expiry before transactional privacy cleanup. Unrelated new records are never swept into an earlier review; linked-content privacy cleanup still applies to reviewed roots. No automatic purge runs. Unsaved memory editor content stays in RAM and is discarded on screen exit/recreation, without Android saved-instance persistence. See the [memory verification report](docs/PHASE_5_VERIFICATION.md).

Phase 7 processes a bounded English grammar locally and reads saved tasks, explicit nonexpired memory and promises. Person resolution uses saved local names only; no contacts access is requested. Answers show bounded excerpts with incompleteness labels. Submission clears the restorable draft; dismissing the sheet cancels unaccepted processing and clears results. Explicitly accepted mutations complete through durable storage and are reviewable in You. Unaccepted requests/results remain transient. Explicitly accepted task titles and bound action/receipt/audit records are encrypted locally for recovery and replay protection; raw request text is not persisted. Creation undo applies existing privacy cleanup to the original action payload/evidence. Completion undo restores status without deleting the task; later task privacy deletion scrubs both completion and its linked undo records. No requests or records are logged, uploaded or used for training. Failures show generic messages without exception text. The orchestrator has no database write/platform execution dependency. Typed proposals and capability snapshots grant no authority; no automatic memory update or new permission is introduced.


Phase 8 adds confirmed task rename, priority, postponement and permanent deletion, plus approximate reminders. Task edits preserve other fields; revision-checked undo restores only changed fields. Deletion removes personal history and commits a separate generic deletion outcome with no task title/notes. Accepted reminders persist encrypted title, explicit time/zone and audit for recovery. Android WorkManager stores only the reminder UUID as input. Its normal wake-lock/boot/network-state/foreground-service declarations grant no internet access. At dispatch the worker checks the record, policy and notifications again; notification content is private on the lockscreen. Registration, posting and reading are distinct: reading is unknown. Privacy-deleted reminders cannot post even if an old scheduler entry later runs. Already visible system notifications may exist until dismissed/cancelled; deleting app records does not prove a person never saw a notification. No raw requests, records or outcomes are uploaded or used for training.

Phase 10 stores the winner of an explicit task-recommendation query, numeric score components, bounded explanation, task revision and scored-source IDs in encrypted recommendation fields. It does not copy raw request text or task notes. History is a snapshot, not behavioral observation or a live plan. Deleting the task or a scored goal/project/focus preference removes dependent recommendations and redacts their correlated event details. Generic event/request-ID tombstones prevent replay from restoring deleted content. No recommendation content is uploaded or used for training.

Planner snapshots are read transactionally from encrypted local records and hashed in memory for the review/acceptance freshness check; raw titles are not copied into an unencrypted fingerprint. Proposed plans are held only in memory and stored blocks are encrypted under the existing schedule codec. Privacy deletion follows task provenance to generated blocks and scrubs accepted-plan payload, audit and event details. Reminder records remain independently accepted records, consistent with the existing reminder cleanup policy.

## Temporary frontend conversations

Submitted requests and replies stay in ViewModel memory. Rotation and workspace navigation retain that session; New chat and process termination discard it. Messages are not saved to Room, preferences, saved-instance state or logs. The bounded unsent draft may be restored by Android. New chat does not delete saved tasks, memories, people, projects or action history. Only a welcome-completion flag is added to private preferences.

## Explicit discipline records (schema v7)

`habit_definitions`, `daily_checkins` and `habit_ticks` are explicit user records. They are independent of the inferred `habits` table and its behavioral-analysis consent rules. Habit names/descriptions, check-in mood and notes use the existing Keystore-backed AES-256-GCM field cipher with fresh nonces and table/row/column authentication. Mood is an optional integer 1..5 serialized inside its encrypted BLOB, never a plaintext numeric database column.

The following metadata is exposed to anyone who can read the app-private database: record IDs and foreign-key links; local check-in dates; captured entry zone IDs; habit cadence (0 = DAILY, otherwise a Monday-bit-0 through Sunday-bit-6 mask); active state; habit start and exclusive archive dates; completion flags; created/updated epoch-millisecond timestamps; and optimistic revision counters. This metadata can reveal check-in timing, habit schedules, completion patterns and the existence of an optional mood/note, even though personal text and mood values are encrypted. It is retained in plaintext to support indexed date-range selection and integrity checks. Android app-private storage and disabled backups still apply; this is field encryption, not whole-database encryption.

Dates are strict `yyyy-MM-dd` local dates. Entry zone/date pairs are immutable. Writes allow today and the previous seven local calendar days in the current entry zone; future check-ins are rejected. A timezone change never rebuckets existing days. Archive dates are exclusive local dates: max(today in the current zone, latest recorded tick date + 1 day), strictly after the habit start. Restore creates a new definition starting today; archived windows, start dates and cadence are not rewritten. No habit names, descriptions, moods, notes, raw ciphertext or keys are logged or copied into plaintext search/statistics tables.

Discipline reads filter local dates in SQL and accept at most 400 inclusive days per request (enough for a 53-week graph). Tick queries join only the requested check-in dates, and habit queries select only definitions whose date windows intersect the request. Any mood averages must be computed transiently in app code from a bounded date-range result, never by SQL aggregation of plaintext mood or by loading entire history. A bounded key-readability probe (LIMIT 1) protects reads/writes, including writes through older repositories when only new discipline ciphertext exists. Missing/wrong keys or authenticated-decryption failures do not clear records, silently return replacement data, or generate a replacement key on reads. Explicit writes use transactions and optimistic revisions; no UI, proposal/accept flow, new permission, network access or analysis consent is introduced in this phase.

Phase 4 trends and gentle observations are computed on device when the Insights screen reads bounded discipline records. Their derived values and dismissed cards are not stored or exported; only the show/hide setting is kept in existing app-private preferences. Free-text notes are neither read nor analyzed. Phase 5 export does not include these transient insights. This adds no database field, permission or external exposure.
